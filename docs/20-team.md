# 봄내마실 — 역할과 협업

> 전원 필독. 원칙은 하나다: **역할 = 폴더 = 산출물.** 두 사람이 같은 파일을 고치는 상황을 처음부터 만들지 않는다.

## 1. 역할 한눈에

| 코드 | 역할 | 담당 (확정) | 소유 폴더 | 만드는 것 |
|---|---|---|---|---|
| R1 | 프론트엔드·디자인 | **우영찬** (@ychanwoo) | `frontend/` | 화면 6종 전부, 지도, QR/코드 인증 화면 |
| R2 | 백엔드·인프라 | **김태우** (@TaeWooKim-SCH) | `backend/` (services 제외) | API 14개, DB 구조, 배포, 오프라인 스택 |
| R3 | 데이터·점수 | **최우혁** (@dngur500-prog) | `pipeline/`, `services/scoring/` | 데이터 10종 적재, 접근성 점수표, 5지표 점수, 대시보드 지도 데이터 |
| R4 | 조립·AI | **최서준** (@Choi-SeoJun, 팀장) | `services/quest_builder/`, `services/llm/` | 퀘스트 조립(걸러내기·빈결과 방지), AI 문안·기록, 데모 대본, 발표 자료 |

각자 "하지 않는 것"이 곧 경계다:
- **R1**: 서버 내부·데이터를 고치지 않는다. 데이터가 이상하면 이슈로 던지고 자기 레인을 유지한다
- **R2**: 점수 산식과 AI 문구 내용에 관여하지 않는다. R4의 조립 함수를 호출만 한다
- **R3**: 화면·API를 만들지 않는다. 점수는 함수로 제공한다. **환승 없이 갈 수 있는지 판별은 R3만 한다** (다른 사람은 결과 조회만 — 두 군데서 계산하면 반드시 어긋난다)
- **R4**: 점수 산식 내부와 DB 구조를 건드리지 않는다 (필요하면 R2·R3에게 요청)

**백업 페어: R1↔R4, R2↔R3.** 한 명이 아프거나 막히면 페어가 이어받는다. 그래서 통합 때마다 페어에게 15분 "실행 워크스루"(내 코드 받아서 켜보기)를 한다. 데모 시연 조작은 반드시 2명 이상이 연습해 둔다.

## 2. 담당 확정 (2026-07-30 팀 결정)

R1 우영찬 / R2 김태우 / R3 최우혁 / R4 최서준(팀장) — 1장 표가 정본이다. 스파이크(#15, #16)는 담당 확정 조건에서 **본선 전 기술 워밍업**으로 성격이 바뀌었다: R1(우영찬)은 카드 목록·지도 마커·QR 스캔 3종을, R4(최서준)는 미니 조립 코드를 본선 전에 한 번 돌려보고 막히는 지점을 미리 발견할 것. 막히면 기존 플랜B(QR→코드 강등, 조립 코어 R2 지원)가 그대로 유효하다.

팀장 규칙: 팀장(최서준)은 R4와 겸직하며 통합 진입 판정·범위 축소 결정을 맡되, **판정은 미리 정한 체크리스트 확인**으로만 한다. 팀장=R4 조합의 이점: 발표 자료·데모 대본 소유자(R4)가 곧 발표 총괄이라 이관 비용이 없다. 발표 연습 시간(H28~30)을 반드시 확보한다.

## 3. 저장소 규칙

- **저장소는 하나다.** R3·R4 코드가 `backend/` 안에 있어도 문제없다 — 폴더 단위로 주인이 있고, 코드 연결은 한 방향 화살표(`routers → quest_builder → scoring`)로만 한다. 남의 부품은 공개된 함수만 가져다 쓴다.
- **브랜치**: `main` 하나 + 작업 브랜치 `feat/<이슈번호>-<역할>-<요약>`. 브랜치 만들고 커밋·푸시하는 건 전원 자유. 작업 브랜치 수명은 반나절 이하 — **자주 합쳐야 통합이 가벼워진다.** 3시간 넘게 안 합친 브랜치는 위험 신호
- **머지**: squash(합칠 때 커밋 1개로 뭉침) 통일. **main으로 들어가는 모든 머지는 PR + R2(태우) 승인 필수** — CODEOWNERS가 태우 단독이라 기술적으로도 강제된다. 대신 태우는 **PR 승인을 10분 내** 처리한다(같은 방에 있으니 가능) — 승인이 병목이 되면 이 규칙이 무너진다
- 폴더 내용을 잘 아는 사람의 리뷰가 필요하면 PR에서 백업 페어를 수동으로 리뷰어 지정한다 (승인 권한과 별개)
- 통합 구간의 main 직커밋은 관리자(태우)만 가능 — 다른 사람 작업분은 태우가 대신 반영한다
- **통합 1시간 전 "머지 마감"** 콜 — 통합 시간은 합치는 시간이 아니라 확인하는 시간이다
- 충돌이 나면 먼저 올린 사람이 아니라 **그 폴더 주인이 해결**한다

### 3-1. 이름 짓기 컨벤션 — 외울 건 이 표 하나다

| 대상 | 형식 | 예시 |
|---|---|---|
| 브랜치 | `feat/<이슈번호>-<역할>-<짧은요약>` | `feat/34-r2-verify-api` |
| 커밋 메시지 | `[역할] 무엇을 했는지 (#이슈번호)` | `[R2] 인증 API 3방식 추가 (#34)` |
| PR 제목 | 커밋과 같은 형식 | `[R1] 추천 화면 카드 3장 (#23)` |
| PR 본문 | 템플릿 자동 적용 — 확인 방법 1줄 + `Closes #번호` | `Closes #23` |

- squash 머지라서 **PR 제목이 곧 main의 기록**이 된다. 중간 커밋 메시지는 대충 써도 되지만 PR 제목만은 형식을 지킬 것
- PR 본문에 `Closes #번호`를 쓰면 머지되는 순간 이슈가 자동으로 닫힌다 — 보드 정리가 공짜가 된다
- 버그 발견 시 새 이슈는 저장소의 버그 템플릿으로 등록한다 (증상·재현 방법·어느 화면인지)

### 3-2. 코드 스타일과 비밀값

- **스타일 논쟁 금지 — 포매터(자동 정렬 도구)에 위임한다.** Python은 `black`+`ruff`, 프론트는 `prettier`. 저장할 때 자동 실행되게 에디터에 설정하고, 코드 리뷰에서 들여쓰기·따옴표 얘기는 하지 않는다
- **비밀값(API 키 등)은 절대 커밋하지 않는다.** 키는 각자 `.env` 파일에만 두고(`.gitignore`에 이미 등록됨), 어떤 키가 필요한지는 값 없는 `.env.example`을 커밋해 공유한다. 실수로 키를 올렸으면 숨기지 말고 즉시 단톡 공유 + 해당 키 재발급
- **일부러 안 쓰는 것들**: develop 브랜치(gitflow), 커밋 타입 규격(feat/fix/chore...), rebase — 30시간짜리 프로젝트에는 규칙 유지 비용이 이득보다 크다. 위 표 하나로 충분하다

## 4. 미리 약속하는 것 4가지 (Day 0 동결)

4명이 서로 기다리지 않고 달리려면, 부품이 만나는 접점을 먼저 확정해야 한다:

| # | 약속 | 누가 → 누구 |
|---|---|---|
| ① | API 명세 (`30-api-contract.md`) — 화면↔서버의 모든 요청·응답 형식 | R2 → R1 |
| ② | 점수 함수 형식 + 접근성 점수표 구조 | R3 → R4 |
| ③ | 대시보드 지도 데이터 형식 | R3 → R1 |
| ④ | 조립 함수 형식 (`build_quests` — 빈 결과일 때 규칙 포함) | R4 → R2 |

동결 후 변경하려면 해당 관리자 승인 + 단톡 공지가 필요하다. "일단 바꾸고 알리기" 금지.

이 약속이 있으면 각자 **가짜 데이터(목, mock)**로 자기 부분을 완성할 수 있다. 예를 들어 R1은 서버가 없어도 약속된 형식의 가짜 응답으로 전 화면을 만들고, 통합 때 진짜로 바꿔 끼운다.

## 5. 이슈와 마일스톤

**이미 45개 이슈가 등록돼 있다** (라벨 R1~R4, 마일스톤 4개, 각 이슈에 완료 기준 포함). 본선 당일 이슈 쓰느라 시간 쓰지 않기 위해서다.

- **마일스톤 = 통합 게이트 4개**: M0 배선(대회 전) → M1 추천이 뜬다(H12) → M2 전체 완주(H24) → M3 제출·발표(H30). 모든 이슈는 마일스톤에 속한다 — 안 속하는 작업은 지금 할 일이 아니라는 뜻
- **이슈 1개 = 담당 1명 = 2~4시간.** 담당이 2명 이상인 이슈는 만들지 않는다 — 책임이 증발하는 지점이다
- **여러 영역에 걸친 기능은 이슈가 아니라 목표다.** 약속(4장)의 경계선을 따라 역할별 이슈로 쪼갠다. 예: "추천 기능" = R3 점수(#) + R4 조립(#) + R2 API(#) + R1 화면(#) — 넷은 서로 기다리지 않고 가짜 데이터로 병렬 완성, 실제 결합은 통합 게이트에서
- **원인 모를 버그**("카드가 안 떠요"): 증상이 보이는 곳의 주인(화면이면 R1)이 담당으로 시작 → 원인 밝혀지면 실제 주인에게 넘긴다
- **30분 룰**: 30분 넘게 막히면 혼자 파지 말고 단톡에 공유 + 이슈에 `blocked` 라벨. 게이트 판정 때 blocked 목록부터 본다
- **보드**(Todo/Doing/Blocked/Done, 1인당 진행 중 1개): 같은 방에 있는 4명에게 보드는 **소통 수단이 아니라 기록 수단**이다. 결정은 입으로, 상태는 보드로. "이슈에 써놨는데요"는 소통이 아니다
- **스탠드업**: 4시간마다 5분, 서서. 직전 결과 / 다음 목표 / 막힘 여부만

### 5-1. 기획에 빈 곳이 발견되면 — 10분 결정 프로세스

만들다 보면 기획서에 없는 질문이 반드시 나온다("추천이 0개면 무슨 문구를 보여주지?", "예산을 조금 넘는 카드도 보여줄까?"). 이런 **기획 공백**을 처리하는 규칙:

**0단계 — 문서 먼저.** 제출 기획서 PDF와 `00-overview.md`에 답이 있으면 그게 답이다. 논쟁은 그다음이다.

**세 급으로 나눠, 결정자를 다르게 둔다:**

| 급 | 예시 | 결정자 | 방법 |
|---|---|---|---|
| ① 사소한 것 (되돌리기 쉬움) | 문구, 버튼 위치, 색 | **발견한 사람이 즉시** | 정하고 PR에 한 줄 남긴다 — 묻지 않는다 |
| ② 동작 규칙 | 빈 결과 처리 방식, 인증 실패 메시지, 스탬프 보상 | **기획 오너 R4(우영찬)** | 담당자가 안(案) 1개를 들고 가서 10분 내 결정 |
| ③ 범위·일정에 영향 | 기능 추가/삭제, 데모 시나리오 변경 | **팀장** | 즉석 소집. 판단 기준은 7장 범위 컷 순서 |

**10분 룰**: 기획 토론은 10분 제한. 합의가 안 되면 위 결정자가 정하고 전원이 따른다. 해커톤에서 최악의 결정은 "결정을 미루는 것"이다. 갈릴 때의 기준 순서: ① 데모 시나리오에 보이는 쪽 ② 구현이 싼 쪽.

**안을 들고 가라**: "어떻게 할까요?"(열린 질문)가 아니라 "A로 하려는데 괜찮아요?"(닫힌 질문)로 묻는다. 열린 질문은 10분을 다 쓰고, 닫힌 질문은 1분에 끝난다.

**기록 — 결정은 반드시 셋 중 하나로 남긴다** (입으로만 정하면 4시간 뒤 같은 질문이 또 나온다):

1. 진행 중인 이슈에 관한 결정 → **그 이슈에 댓글** (결정 내용 + 결정자 이름)
2. 새 작업이 생기는 결정 → **새 이슈 등록** (1담당·마일스톤 필수 원칙 그대로). 지금 마일스톤에 못 붙는 아이디어면 `later` 라벨을 달아 본선 이후 백로그로 — 보드에서 치운다
3. 서비스의 정의가 바뀌는 결정 → **`00-overview.md` 수정 PR** — 문서가 낡으면 다음 사람이 같은 질문을 또 한다

## 7. 시간이 없을 때 버리는 순서

1. AI 유사도 정렬 (키워드 매칭만으로 시연 — 기획서에도 2차로 명시돼 있어 방어 가능)
2. 대시보드 사각지대 지도 (히트맵·저유입 2종은 유지)
3. 영수증 인증 (업로드까지만 — 단, 발표에서 "소비 지표" 설명은 유지)
4. QR 카메라 (4자리 코드로 시연 — "어르신 배려 경로"라는 서사로 전환 가능)
5. 스탬프 연출 (적립 숫자만)

**절대 못 버리는 것**: 입력→추천→상세→인증→기록의 전체 완주, 그리고 만14세 확인·기록 삭제 버튼(개인정보 설계의 방어선).
