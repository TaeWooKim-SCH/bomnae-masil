> 이 서비스의 재료 전부. 제출 기획서 3-6장(활용 데이터 목록)·6장(추가 요청)을 옮기고 실무 정보를 붙인 것이다.
> R3(데이터 담당)의 수집 기준 문서이며, 수집하면서 "확보" 칸과 다운로드 URL을 채워 살아있는 문서로 유지한다.

## 3. 춘천시에 추가 요청한 데이터 3종 (기획서 6장 — 제공 시 고도화)

기획서에서 춘천시가 단독 보유한 데이터의 공개를 공식 요청했다. **본선 전 제공 여부를 주최 측에 확인**하고, 오면 아래 용도로 쓴다. 안 와도 MVP는 위 10종만으로 돈다.

| 요청 데이터 | 형식 | 쓰임 |
|---|---|---|
| 춘천사랑상품권 가맹점 목록 (업종 포함) | CSV/API | 가게 미션을 지역화폐 가맹점 중심으로 구성 — 방문이 지역화폐 결제로 이어지는 선순환 |
| 시립도서관·문화시설 프로그램 정보 | CSV/API | 활동 후보군 확대 — 무료·저비용 활동 비중 상향 |
| 행정동 단위 시간대별 유동인구 | CSV/API | 저유입 시간대 분석 정밀화 (현재는 #3 승하차량을 대리 지표로 사용) |

## 4. 수집·관리 규칙

1. **스냅샷 원칙**: 시연일 기준으로 한 번 내려받아 고정본을 쓴다 (본선장에서 새로 받지 않는다). 원본 파일은 저장소가 아니라 **팀 드라이브에 공유**하고 `pipeline/snapshots/`는 `.gitignore` 처리돼 있다
2. **춘천 필터 선적용**: 전국 단위 데이터(특히 #9 인허가 — 수 GB급)는 내려받은 뒤 적재 전에 춘천만 걸러낸다. 안 그러면 DB 무료 용량(500MB)을 바로 초과한다
3. **종료된 것 걸러내기**: 기간이 지난 행사·강좌는 적재 단계에서 제외한다
4. **측정 이력 없음 = 저유입 추정 후보**: #4 실태 데이터에 없는 가게는 "데이터가 없다"는 이유로 저유입 확정하지 말고, 보수적으로 '추정 후보'로만 분류한다 (기획서에 약속한 편향 방지 원칙)
5. 데이터마다 **기준일·행 수·출처 URL**을 이 문서에 기록한다 — 심사 질의("이 데이터 어디서 났나요")에 문서로 답한다
